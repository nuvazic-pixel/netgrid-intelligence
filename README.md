# NetGrid — FTTH Infrastructure Scenario Dashboard
**Python · pandas · SQLite · Streamlit · Plotly · PyDeck**  
Portfolio prototype connecting telecommunications field experience with analytical reporting.

## Business question
How do subscriber take rate, construction cost and recurring revenue assumptions affect an FTTH rollout scenario, and how can those assumptions be explained to a project team?

## Start here
- **[Executed scenario comparison](reports/take_rate_scenarios.md)** — three explicit take-rate assumptions, an exact results table and interpretation.
- [Machine-readable scenario results](reports/take_rate_scenarios.csv).
- [Reproduce the example](examples/scenario_report.py).
- [Dashboard](app.py), [calculations](calculations.py), [SQLite data layer](db_layer.py) and [rule-based scoring](ai_swarm.py).

## What the project demonstrates
1. Organising municipal-style records and simulated FTTH metrics in SQLite.
2. Comparing CAPEX, subscribers and annual sales-value assumptions.
3. Exploring maps, filters and scenario sensitivities in a Streamlit interface.
4. Explaining conservative, aggressive and balanced scoring perspectives through transparent Python rules.
5. Keeping observed inputs, simulated metrics and model assumptions separate.

## Example result
The reproducible example holds 3,000 homes, EUR 900 CAPEX per home and EUR 40 monthly ARPU constant. At 30%, 45% and 60% take rate, the existing calculation produces 900, 1,350 and 1,800 subscribers, respectively.

This demonstrates sensitivity to assumptions. It does not predict take-up for any municipality.

## Data provenance
The demo seed in `db_layer.py` contains 30 named Bavarian municipalities with coordinates and demographic inputs entered in code. These entries have not been independently verified against current official sources in this portfolio revision.

FTTH adoption, coverage, infrastructure distance, income proxies and competitor metrics generated by the demo are **simulated**. Household counts are estimates. Other experimental data modules also exist in the repository; do not assume all modules share the same provenance.

## Analytical approach
| Component | Purpose |
| --- | --- |
| `db_layer.py` | Initialise SQLite records, expose DataFrames and persist scenario decisions |
| `calculations.py` | Scenario calculations, cash-flow projections, NPV sensitivity and break-even exploration |
| `ai_swarm.py` | Three rule-based scoring agents and a consensus mechanism |
| `app.py` | Streamlit presentation, charts, filters and maps |
| `examples/scenario_report.py` | Small deterministic example using the existing scenario calculation |

The three agents are rule-based Python logic, not trained predictive models or independent evidence of investment success. Confidence and consensus fields are heuristic scores, not calibrated probabilities.

## What this project practises
- Translating FTTH terminology into explicit data fields and reporting metrics.
- Keeping calculation logic separate from presentation.
- Building scenario comparisons with controlled assumptions.
- Showing how changing one input affects a business metric.
- Communicating data provenance, model limitations and reproducibility.

## Run locally

cd netgrid-intelligence
python -m venv .venv
# Activate .venv using the command for your operating system.
python -m pip install -r requirements.txt

The core scenario example does not require API keys. Some geographic features may depend on external services.

## Validation and model limits
- The published scenario example was executed against the existing `calc_scenario` implementation. The full Streamlit interface and external integrations were not exercised in this revision.
- The example applies the model's fixed 30% revenue-based OPEX assumption. Its operating surplus is a simplified proxy, not an audited EBITDA or cash-flow forecast.
- The financial helpers are exploratory. Payback/IRR edge cases and assumptions across helper functions require further validation before commercial use.
- Simulated municipal metrics use Python's process-dependent hash in their seed, so regeneration is not guaranteed identical across processes.
- This is a learning/portfolio prototype, not a production investment decision service.

## Financial model verification

`calculations.calc_roi` computes payback from cumulative, undiscounted cash flows,
including the configured churn and OPEX assumptions. It returns `payback=None`
when capital is not recovered within `horizon_years`; recovery at the final year
still counts. The dashboard and executive report show this explicitly rather
than substituting the modeled horizon as a recovery date.

Run the financial regression tests from the repository root:

```bash
python -m pip install "numpy>=1.26.0" "pandas>=2.0.0"
python -m unittest discover -s tests -v
```

These tests cover the financial model and its payback presentation helpers.
They do not validate real-world adoption, investment returns, or the full dashboard.
